# OCR alternative recommendation — metadata research, 2026-10-28

**Probe PP-OCRv5 mobile detection plus English mobile recognition first.** Keep Apple Vision as the working baseline. Use Tesseract `eng` fast as a smaller native comparator; reserve PaddleOCR-VL with MLX for a later document-parsing experiment. This order is an engineering recommendation based on task fit, upstream Mac support and dependency size, **not a measured accuracy ranking**. Nothing here is installed, implemented, inference-tested, registered, or approved for deployment.

## Actual upstream Mac setup paths — commands not executed

Paddle's Apple Silicon guide installs `paddlepaddle==3.2.1` from its CPU index and `paddleocr[doc-parser]` for VL. For the smaller OCR-only probe, use an isolated Python 3.12 environment with a separately resolved `paddleocr==3.7.0` / PaddleX 3.7 lock and that CPU runtime. The 3.7 version comes from current publisher metadata; this exact combination has not been tested here. Start with `device='cpu'`, bounded `cpu_threads=4`, local detector/recognizer directories and explicit PP-OCRv5 names. Disable document orientation, unwarping and text-line orientation initially so no unpinned auxiliary weights are fetched. Pin transforms, dictionaries and character set as well as the weight files. The [official OCR parameters](https://github.com/PaddlePaddle/PaddleOCR/blob/dab3fe35379033fdcb2d0e9572fac0b36c9a9ebf/docs/version3.x/pipeline_usage/OCR.en.md) document local paths and warn that absent paths trigger downloads.

For VL, the same official guide specifies `mlx-vlm>=0.3.11`, `mlx_vlm.server --port 8111`, and Paddle's `vl_rec_backend='mlx-vlm-server'` plus local service/model-path parameters. It does not support its official Docker image on this hardware. A future app probe must explicitly bind loopback and verify identity, bounded inputs, timeout/cancellation and offline behavior. The current MLX-VLM 0.7.11 package metadata requires `transformers>=5.14.0`; the app uses 4.57.6. **Use a separate process/environment; do not upgrade the app's transformer stack.** The VLM's generated strings are recognition hypotheses; do not synthesize per-character confidence or substitute expected answers into a prompt. An OCR-only crop experiment and a complete document pipeline must be named and scored separately.

Tesseract's upstream route is `brew install tesseract`, with optional language packages. A future isolated probe can invoke an absolute binary path and a pinned `--tessdata-dir`, `-l eng --oem 1 --psm 7` for known single lines. Use a separately fixed page segmentation mode for whole frames; never choose the mode from the answer. Shipping the brew binary is not proof of relocation/signing portability. Do not install system packages during the current freeze.

## Proposed adapter boundary

A future adapter should return raw recognized text, optional native confidence, optional region polygon, model/config identity, and runtime timings from a local image/crop. Missing confidence stays absent. It must not spell-correct, case-fold, drop leading zeros, normalize punctuation, use an expected code as a decoding hint, or silently fall back to Apple Vision. Expected-text comparison remains a separate deterministic pipeline step. Barcode decoding remains a different capability: OCR reading printed digits does not validate a barcode payload.

The existing Apple Vision adapter currently returns text strings, so compare common text outputs first. Any richer region/confidence contract needs a deliberate compatible schema change. Existing `text_accuracy`, CER and WER evidence can be reused with their documented normalization; do not merge box-based scores with text exactness. A future installed adapter remains unchecked until an identity-bound real smoke test and offline failure checks complete. Catalog promotion is outside this research task.
